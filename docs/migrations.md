# Configuration Migrations

This document tracks every breaking change to the `rustgate.toml`
configuration schema, organised by source-version → target-version
transitions, plus the operator-facing tooling that rewrites old configs
into the schema this binary understands.

The framework is the v1 deliverable of issue #815 (F-138). The other
two halves of #815 are:

- **F-136** — config validation consolidation, shipped via #1244. The
  `validate-config` subcommand catches schema drift after migration.
- **F-137** — JSON Schema export, shipped via #1259. The
  `emit-schema` subcommand emits a JSON Schema for the *current*
  TOML shape; this doc tracks the per-version *deltas*.

## When to migrate

Run `rustgate migrate-config <PATH>` whenever:

1. You upgrade rustgate across a release that lists key renames or
   removals in the matrix below, and your existing config still uses
   the old spelling.
2. CI fails a `validate-config` check on a previously-working config —
   the failure is almost always a schema-drift issue migration can
   fix.
3. You inherit an old `rustgate.toml` (e.g. from a backup or another
   operator's deployment) and want to bring it forward to the
   currently deployed binary's schema.

## How the tool decides what to do

The chain runs in three stages:

1. **Detect source version.** In priority order:
   - `--from <version>` (operator override)
   - `# rustgate-version: <version>` comment in the input
   - heuristic check for known-obsolete top-level keys
   - fallback: assume the binary's current schema (no-op pass)
2. **Apply migration chain.** For every step between source and
   current: rename, drop, restructure. Keys that don't appear in the
   step's vocabulary pass through unchanged.
3. **Stamp the banner.** A `# Generated by rustgate migrate-config
   from <source>` line is added at the top of the output. Idempotent
   across repeated runs.

Comments and blank lines survive every transition because the rewriter
uses `toml_edit` rather than round-tripping through the typed
`ConfigFile` deserialiser. If you annotated `# Operator note: this is
the production cert` above the legacy `tls_cert` key, that line lands
above the renamed `cert` key.

## Usage

```bash
# Detect source automatically and write to stdout
rustgate migrate-config rustgate.toml

# Override detection (use this when the heuristic is wrong, or when
# you want to force the chain to run on an unmarked file)
rustgate migrate-config rustgate.toml --from pre-0.8

# Persist to a new file and validate end-to-end
rustgate migrate-config rustgate.toml --output rustgate.next.toml
rustgate --config rustgate.next.toml validate-config
```

A hand-edited `# rustgate-version: 0.7` comment at the top of an old
file is the most maintainable way to pin the source version — the
banner that the tool stamps after a successful migration takes over
that role going forward.

## Recognised source versions

| Token | Aliases accepted by `--from` | Description |
|-------|------------------------------|-------------|
| `pre-0.8` | `pre-v0.8`, `0.7`, `0.7.0` | Synthetic baseline covering every release before the schema was formalised. |
| `0.8` | `v0.8`, `0.8.0` | First release with a stable, documented schema. Currently the chain's terminal version. |

`--from` rejects every other value with a typed
`unrecognized version: <value>` error and a non-zero exit code so a CI
wrapper can branch on the failure mode without parsing stderr.

## Upgrade matrix

### `pre-0.8` → `0.8`

The first formal migration. rustgate prior to 0.8 used three
TLS-prefixed key names that have since collapsed onto the shorter
spellings now used by the CLI flags and environment variables.

| Action | Pre-0.8 key | 0.8 key | Notes |
|--------|-------------|---------|-------|
| Rename | `tls_cert` | `cert` | TLS server certificate path. Matches the `--cert` flag and `RUSTGATE_CERT` env var. |
| Rename | `tls_key` | `key` | TLS server private key path. Matches the `--key` flag. |
| Rename | `tls_ca` | `ca` | Trusted CA bundle path. Matches the `--ca` flag. |
| Drop | `legacy_xml_strict` | — | Removed: XML strict parsing is now governed by `--framing` selection, not a separate Boolean. The migration emits a warn-level event on stderr (`migrate-config: [warn] dropping obsolete config key 'legacy_xml_strict' …`) so an operator who relied on the knob notices. |

### `0.8` → `0.8`

No-op. Runs the chain with zero key-level actions and stamps the
banner. The pass is idempotent — running migrate-config twice on the
same input produces the same output.

## Adding a new transition

When a future PR introduces a breaking config change:

1. Append a new variant to the `Version` enum in
   `crates/rustgate-server/src/diagnostics/migrate_config.rs`. Keep
   chronological ordering — new variants always go at the end so the
   `PartialOrd` derive continues to encode "newer = greater".
2. Update `Version::current()` to point at the new variant and extend
   `Version::parse` with the canonical and aliased strings the
   operator-facing flag should accept.
3. Add a new `Migration` impl that mutates the `DocumentMut` from the
   previous version to the new one. Keep the impl pure — no I/O.
4. Wire the new step into `chain_for(source)` so it runs whenever the
   detected source is at-or-below the previous version.
5. Add a row to the matrix above describing every key the migration
   touches and the operator-facing rationale.
6. Add an integration test under
   `crates/rustgate-server/tests/migrate_config.rs` that pins the
   rename / drop semantics for the new transition. The existing tests
   are templates — copy a rename test, swap in the new keys, assert
   on the rewritten output.
7. Update the `[Unreleased]` section of `CHANGELOG.md` describing the
   schema break and pointing to this doc.

The framework is intentionally minimal: each transition is one struct,
one `Migration` impl, and one row in this doc. That keeps the
operator-facing surface (`--from <version>`) and the tooling behaviour
(`migrate-config <path>`) trivially discoverable as the schema
evolves.

## Limitations

Out of scope for v1 — these may land in follow-ups if the operator
demand surfaces:

- **Online migration.** The subcommand rewrites a TOML file. Servers
  with a long-running config-reload loop (`SIGHUP`) need a restart to
  pick up the migrated file.
- **Two-way migrations.** The chain only walks forward (older →
  newer). Downgrades are unsupported because they would require
  re-introducing keys the new schema deliberately removed.
- **Restructured tables.** v1 only handles flat top-level renames and
  drops. A future migration that splits a flat key into a `[section]`
  table or merges a table back into top-level keys will need new
  migration helpers — the existing `MigratePreV08ToV08` is a usable
  starting point.
