## [Unreleased]

### Security

- **Case-insensitive CN matching in ACL** — `GroupAcl` now normalizes all certificate Common Name strings to ASCII lowercase at construction time and before lookup, matching the case-insensitive semantics required by RFC 5280 §7.1. Previously, an attacker with a differently-cased CN (e.g. `CN=Admin` vs. `admin`) could bypass ACL rules. (#652)
- **Default-deny for unconfigured groups when ACL policy is loaded** — `GroupAclPolicy` now denies send and receive for groups that have no explicit ACL entry when at least one other group is configured. Previously, unconfigured groups defaulted to open, which could silently expose groups omitted from the policy file. When no policy is loaded at all (empty map), the router continues to operate in open mode for backward compatibility. (#653)
- **Federation peer identity from TLS certificate** — federation server now extracts peer identity from the mTLS client certificate CN instead of the remote IP address, preventing impersonation behind NAT/load balancers. Falls back to IP with a warning when certificates are unavailable. (#655)
- **Federation hop count validation** — inbound federated events with a hop count exceeding the configurable maximum (default 8) are dropped with a warning, preventing routing loops between federation peers. (#657)
- **ACL re-check on store-forward delivery** — messages drained from the offline queue are now filtered through the current ACL and authorization policies before delivery. This prevents messages stored under a previous policy from being delivered after the sender's permissions have been revoked. (#651)
- **Per-session non-blocking delivery** — direct and broadcast message delivery now uses non-blocking channel sends (`try_send`), preventing a single slow consumer from starving all other sessions. Messages to full channels are persisted for offline delivery (direct) or dropped (broadcast) instead of blocking the routing task. The global backpressure gate is retained for overall memory protection. (#656)
- **Federation peer group validation** — validate federation peer group membership on inbound messages; peers can only inject events into groups they are explicitly authorized for. When no per-peer group allowlist is configured, all messages pass (backward compat). (#658)
- **RUSTSEC-2026-0002 — bump `lru` to 0.16.3** — the `lru` crate versions `>=0.9.0, <0.16.3` contained a soundness issue where `IterMut::next`/`next_back` temporarily created an exclusive reference to the key, invalidating the shared pointer held by the internal `HashMap` and violating Stacked Borrows. rustgate transitively pulled in `lru 0.12.5` via `rustgate-transport`. The workspace dependency has been bumped to `0.16.3`, which contains the upstream fix. (#582)
- **CSR signature verification** — documented and tested that CSR self-signatures are verified before certificate issuance, preventing forged-subject attacks. rcgen's `CertificateSigningRequestParams::from_pem()` internally calls `x509_parser` signature verification, rejecting CSRs where the public key does not match the self-signature. (#654)

### Fixed

- **Per-session non-blocking delivery** — direct and broadcast message delivery now uses non-blocking channel sends (`try_send`), preventing a single slow consumer from starving all other sessions. Messages to full channels are persisted for offline delivery (direct) or dropped (broadcast) instead of blocking the routing task. The global backpressure gate is retained for overall memory protection. (#656)

- **Federation TTL re-check at forward boundary** — the federation manager now re-evaluates each message's TTL immediately before queuing it to peer outbound channels via the new `FederationManager::forward_with_metadata` API. Messages whose `received_at + ttl` has elapsed between local routing and federation forwarding are dropped with a warning instead of consuming peer bandwidth. A new `rustgate_federation_forward_ttl_expired_total` Prometheus counter (under the `api` feature) tracks drops, and the `federation` snapshot endpoint exposes the same value as `forward_ttl_expired`. The legacy `forward(payload, groups)` entrypoint is preserved for callers that have no TTL context. (#554)

### Added

- **Documentation site scaffold (GitHub Pages)** — new `docs-site/` mdBook project and `.github/workflows/docs.yml` GitHub Actions workflow publish a structured public documentation site to GitHub Pages on every push to `main`. The site organizes getting-started guides, architecture, operations runbooks, API reference, security analysis, and a research section (why rustgate, comparison to alternatives, exploit resistance matrix, benchmarks, and downloadable papers). The workflow also builds `cargo doc --workspace --no-deps` and mounts it at `/api/rustdoc/` alongside the book. Preprocessors wired in: `mdbook-mermaid` (diagrams), `mdbook-admonish` (callouts), `mdbook-toc` (per-page TOC), and `mdbook-linkcheck` (CI link validation). MathJax is enabled for research pages. The initial commit seeds the exploit-resistance matrix and the "why rustgate" advocacy page with real content; remaining pages are stub placeholders to be filled in subsequent PRs.
- **MQTT 5.0/3.1.1 transport adapter** — new `rustgate-mqtt` crate adds an MQTT transport with mTLS client authentication. Supports CONNECT/CONNACK handshake with protocol-level negotiation, PUBLISH (QoS 0 and 1, QoS 2 rejected), SUBSCRIBE with dynamic group membership via `Router::join_group`/`leave_group`, UNSUBSCRIBE, PINGREQ/PINGRESP, and clean DISCONNECT. MQTT topic names map bidirectionally to rustgate routing groups, with an optional configurable prefix (`--mqtt-topic-prefix`). Certificate OU fields serve as the authorization boundary — clients can only subscribe to groups listed in their certificate. New CLI flags: `--mqtt-bind` (env `RUSTGATE_MQTT_BIND`), `--mqtt-topic-prefix` (env `RUSTGATE_MQTT_TOPIC_PREFIX`), `--mqtt-max-packet-size` (env `RUSTGATE_MQTT_MAX_PACKET_SIZE`, default 16 MiB). Gated behind the `mqtt` feature flag. (#567)
- **Per-message RBAC/ABAC authorization** via the new `rustgate-authz` crate. Policies are loaded from a JSON file with deny-by-default semantics, hot-reloaded on file changes (last-good preserved on validation failure), audited on every deny and reload outcome, and exposed via Prometheus metrics. A sharded LRU keyed on policy epoch evaluates in <100ns P99 on cache hits, well under the 10µs budget enforced by a per-PR criterion-based perf gate. Optional Cedar policy backend behind the `cedar` feature. New CLI flags: `--authz-policy-file`, `--authz-policy-format`, `--authz-reload-interval`, `--authz-fail-open`. Identity now carries a SPIFFE ID and an attribute bag derived from mTLS cert SANs and subject fields. Closes #563.
- **Per-UID CoT delta encoding for outbound XML sessions** — CoT track sources emit periodic position updates where the bulk of each event body is unchanged between pings. Rustgate can now track the last-sent event per `uid` on a per-writer basis and emit a compact `<delta>` wrapper carrying only the fields that changed, saving bandwidth on dense position workloads. Opt-in via the new `--cot-delta-encoding` CLI flag (env `RUSTGATE_COT_DELTA_ENCODING`, default off); disabled by default so existing deployments are unaffected. The encoder cache is bounded per writer via `--cot-delta-cache-size` (env `RUSTGATE_COT_DELTA_CACHE_SIZE`, default 512 entries, LRU eviction) and position-only drift below `--cot-delta-epsilon-meters` (env `RUSTGATE_COT_DELTA_EPSILON_METERS`, default 1.0 m ground distance) is suppressed entirely so a jittery GPS cannot flood subscribers. The first event for any UID is always emitted in full so new subscribers reconstruct state from an empty cache automatically; immutable attribute drift (`version`, `type`, `how`) also forces a full re-emit. Only XML-framed sessions (protocol id `tak-xml`) are wrapped — protobuf, length-prefixed, and line-delimited sessions pass through unchanged. Four new Prometheus counters (`rustgate_cot_delta_full_total`, `rustgate_cot_delta_delta_total`, `rustgate_cot_delta_suppressed_total`, `rustgate_cot_delta_bytes_saved_total`) are registered under `--features metrics` so operators can compute the compression ratio and suppression rate. See `docs/cot-delta-encoding.md` for the wire format. (#568)
- **Dynamic federation peer discovery (DNS-SD, Consul, etcd)** — the federation manager can now resolve its peer list from three external service registries instead of a static `--federation-peers-file`. New `--federation-peer-discovery <none|dns-sd|consul|etcd>` CLI flag (env `RUSTGATE_FEDERATION_PEER_DISCOVERY`) selects a backend, and `--federation-peer-discovery-interval` (env `RUSTGATE_FEDERATION_PEER_DISCOVERY_INTERVAL`, default 30 s) sets how often a background reconciler re-polls the source and feeds the result into the existing `FederationManager::swap_peers` API from #556 — so adds, removes, and replays all go through the same zero-downtime path as the file reloader. The DNS-SD backend (`--federation-peer-discovery-dns-sd-service`, default `_rustgate._tcp.local.`) browses an mDNS service type and materialises each resolved instance as an outbound peer. The Consul backend (`--federation-peer-discovery-consul-addr`, `--federation-peer-discovery-consul-service`) queries `/v1/catalog/service/<name>` on any Consul HTTP endpoint. The etcd backend (`--federation-peer-discovery-etcd-endpoints`, `--federation-peer-discovery-etcd-prefix`) performs a prefix scan and accepts either raw `host:port` values or serialized `PeerConfig` JSON per key. A new public `PeerDiscovery` trait makes the design pluggable so operators can bring their own source. The `--federation-peer-discovery` flag is mutually exclusive with `--federation-peers-file`. Each backend ships behind its own sub-feature (`peer-discovery-dns-sd`, `peer-discovery-consul`, `peer-discovery-etcd`) with an umbrella `peer-discovery` feature that enables all three, so minimal images only pay for the registry they actually use. Selecting a backend whose feature was not compiled in fails fast at startup instead of silently ignoring the setting. (#571)
- **OTLP metrics export alongside Prometheus** — new `--otlp-metrics` CLI flag (env `RUSTGATE_OTLP_METRICS`, disabled by default) enables pushing rustgate's existing Prometheus metrics over OTLP gRPC to the same collector endpoint already configured for traces via `--otel-endpoint` (env `OTEL_EXPORTER_OTLP_ENDPOINT`). A companion `--otlp-metrics-interval` flag (env `RUSTGATE_OTLP_METRICS_INTERVAL`, default 60 seconds, minimum 1) controls the push cadence. Implemented as a non-invasive bridge: on startup, the OTEL meter walks the Prometheus default registry and attaches one observable instrument per metric family whose callback re-gathers values (including newly-added per-identity label sets) on every collection cycle. Counters map to `f64_observable_counter`, gauges to `f64_observable_gauge`, and histograms/summaries surface as paired `<name>_sum` / `<name>_count` observable counters. The existing `/metrics` scrape endpoint is unchanged — OTLP export is purely additive. Pending metrics are flushed on graceful shutdown so the final batch reaches the collector. Requires `--features otel,metrics`. (#572)
- **SPIFFE / SPIRE workload identity (initial)** — new `spiffe` feature flag (disabled by default) lets rustgate fetch its server TLS certificate, private key, and trust bundle from a SPIRE agent via the SPIFFE Workload API instead of from static files. New CLI flags: `--spiffe` (env `RUSTGATE_SPIFFE`) enables the identity source; `--spiffe-workload-api-socket` (env `RUSTGATE_SPIFFE_WORKLOAD_API_SOCKET`, default `unix:///tmp/spire-agent/public/api.sock`) selects the Workload API endpoint; `--spiffe-trust-domain` (env `RUSTGATE_SPIFFE_TRUST_DOMAIN`) optionally enforces a specific trust domain; `--spiffe-refresh-interval` (env `RUSTGATE_SPIFFE_REFRESH_INTERVAL`, default 300 s) controls the periodic SVID refresh. `--spiffe` is mutually exclusive with `--cert`/`--key`/`--ca`/`--enrollment-bind` at the clap level. The initial X.509-SVID is fetched at startup and seeded into the existing `CertReloader` via a new `CertReloader::from_der` constructor and atomic `CertReloader::update_from_der` path, so subsequent refreshes reuse the same zero-downtime rotation primitive used by file-based hot-reload. A background task re-polls the Workload API on the configured interval and updates the active `CertifiedKey` in place. Two new Prometheus metrics (feature-gated on `metrics` + `spiffe`): `rustgate_spiffe_svid_refresh_total{outcome="success|failure"}` counter and `rustgate_spiffe_svid_expiry_seconds` gauge (unix seconds). Structured `target="audit", event_type="spiffe.svid_refresh"` audit events are emitted on every refresh outcome with `spiffe_id`, `trust_domain`, and `expiry_unix` fields. Depends on the `spiffe` crate (Apache-2.0). Client-side SPIFFE ID extraction (using a connecting peer's URI SAN as its routed identity in place of the X.509 CN) and dynamic trust-bundle rotation are deferred to a follow-up PR; connecting clients continue to authenticate via CN on the existing path. (#570)
- **Grafana dashboards, Prometheus alert rules, and recording rules** — new top-level `ops/` directory ships five importable Grafana dashboards (`rustgate-overview`, `rustgate-transport`, `rustgate-federation`, `rustgate-nats`, `rustgate-enrollment`) using a `${DS_PROMETHEUS}` datasource variable, plus `ops/prometheus/alerts.yml` with alert families covering handshake failure ratio, admission gate saturation, client queue drops, federation peer lag / queue bytes / circuit breaker trips / forward TTL expirations / total peer disconnection, NATS consumer pending / redelivery storms / consumer-info latency, and enrollment rate limiting, and `ops/prometheus/recording-rules.yml` with ten aggregations (message rate, handshake error ratio, federation peer lag, NATS consumer pending, etc.) to speed up dashboard queries. An `ops/README.md` documents the layout, import flow, and rule-file wiring. (#573, #574)
- **Federation frame parser fuzz target** — new `federation_frame_parse` cargo-fuzz target that drives arbitrary bytes through the V1 federation read pipeline (4-byte big-endian length-prefixed codec) and runs `is_heartbeat` on each decoded payload, mirroring the inbound peer read loop. Also exercises the heartbeat fast-path classifier directly on raw input. (#575)
- **EST (RFC 7030) enrollment endpoints** — new `est` feature flag (disabled by default) adds Enrollment over Secure Transport endpoints to the enrollment HTTPS server: `GET /.well-known/est/cacerts` returns the CA certificate chain as a PKCS#7 certs-only bag (RFC 5652), `POST /.well-known/est/simpleenroll` accepts a base64-encoded PKCS#10 CSR and returns the issued certificate plus CA chain as a PKCS#7 certs-only bag, `POST /.well-known/est/simplereenroll` handles re-enrollment (same flow), and `GET /.well-known/est/csrattrs` returns 204 No Content. All responses use base64 per RFC 4648 Section 4 as clarified by RFC 8951. EST endpoints are gated behind the new `--est-enabled` CLI flag (env `RUSTGATE_EST_ENABLED`) and share the existing HTTP Basic auth, per-IP rate limiting, and `CsrSigner` infrastructure. Labeled EST paths (`/.well-known/est/{label}/cacerts`) are supported for multi-CA deployments. New dependencies: `cms`, `der`, `x509-cert` (all optional, only pulled when `est` feature is enabled). (#569)
- **Client certificate OCSP verification (Tier 1)** — new `--client-ocsp` CLI flag (env `RUSTGATE_CLIENT_OCSP`) wraps the active client cert verifier with a SKI-keyed OCSP cache. On a cache miss the inner verifier's decision still stands (fail-open) and a background task fetches an OCSP response via the existing `ocsp-stapler` HTTP client so the *next* handshake for the same certificate can be answered from the cache; cached `Revoked` responses cause the handshake to be rejected before the session is established. Provides near-real-time client revocation as a complement to CRLs, which only refresh on a schedule. Two new Prometheus counters track cache effectiveness: `rustgate_client_ocsp_cache_hits_total` and `rustgate_client_ocsp_cache_misses_total` (both registered under `--features metrics`). Requires `--features ocsp`. (#555)
- **Hot-reloadable federation peers** — the federation peer set can now be reconciled at runtime without restarting the server. New `--federation-peers-reload-interval` CLI flag (env `RUSTGATE_FEDERATION_PEERS_RELOAD_INTERVAL`, default 0 = disabled) enables periodic polling of `--federation-peers-file`, and SIGHUP also triggers a reconcile when the reloader is configured. File changes are detected via SHA-256 hash comparison; only modified files trigger a swap. New peers in the file are connected, peers no longer in the file are gracefully disconnected (their outbound clients shut down, replay buffers cleared, HA claims released when applicable), and peers whose configuration changed are reconnected with the new settings. Peers whose configuration is unchanged are left untouched — existing connections are preserved. New `FederationManager::add_peer`, `FederationManager::remove_peer`, and `FederationManager::swap_peers` APIs back the reloader and return a `PeerSwapDiff` summarising added/removed/unchanged/failed peers. Structured `target="audit", event_type="config.reload", component="federation_peers"` events are emitted on success and failure. Closes the gap left by the SIGHUP-driven ACL reloader, where adding or removing a federation partner still required a full restart. (#556)
- **Encrypted-at-rest CoT archive and audit log** — new `--archive-key-file` CLI flag (env `RUSTGATE_ARCHIVE_KEY_FILE`) enables streaming ChaCha20-Poly1305 encryption of the CoT event archive (when `--archive-dir` is set) and the JSON audit log file (when `--audit-log` is a path). The key file is a small JSON document `{ "active_key_id": "<id>", "keys": { "<id>": "<64-char hex>" } }` where each key is 32 bytes; key material is held in `zeroize::Zeroizing` buffers so it is wiped on drop. Each output file gains a fixed header (magic `RGENC1\0\0` + version + key id + 8-byte random base nonce) followed by length-prefixed AEAD chunks; the per-chunk nonce is the base nonce concatenated with a 32-bit chunk counter, and any single-byte tampering fails AEAD verification on read. Per-chunk AAD binds the key id and chunk counter to detect chunk reordering, and a sealed terminator chunk is written on close so silent tail-truncation is detectable on read. Key rotation is supported by adding a new key id and switching `active_key_id`: historical files written under prior keys remain readable as long as the old key is still listed. A new `rustgate decrypt-archive --in <path> --out <path> --key-file <path>` subcommand round-trips encrypted files back to plaintext for inspection or export. (#561)
- **Persistent federation replay buffer** — federation per-peer replay buffers can now be mirrored to a redb database on disk so they survive server restarts. New `--federation-replay-dir` CLI flag (env `RUSTGATE_FEDERATION_REPLAY_DIR`) enables persistence by pointing at a directory; the store file is `<dir>/federation_replay.redb`. Total on-disk usage is bounded by `--federation-replay-max-bytes` (env `RUSTGATE_FEDERATION_REPLAY_MAX_BYTES`, default 64 MiB) with global drop-oldest eviction across peers. On startup, the federation manager rehydrates each peer's in-memory ring buffer from the store before accepting connections, so a peer that reconnects immediately after a restart resumes replay from its last persisted point instead of seeing an empty buffer. Records whose TTL has already expired at rehydration time are skipped (counted by `rustgate_federation_replay_restored_skipped_ttl_total`) so persistence cannot resurrect messages that should have been dropped. Disabled by default; existing in-RAM-only behavior is unchanged when the flag is not set. (#557)
- **Per-peer federation lag metrics** — two new Prometheus gauges track outbound queue lag for each federation peer: `rustgate_federation_peer_queue_bytes{peer="..."}` exposes the bytes currently queued for delivery, and `rustgate_federation_peer_oldest_seconds{peer="..."}` exposes the age (in seconds) of the oldest message still waiting to be sent. Counters are maintained on the `PeerHandle` (atomic byte counter + FIFO of enqueue timestamps) and updated by both the V1 framed and V2 gRPC client send paths. A 1 s background updater task in the metrics layer snapshots the federation manager and republishes the gauges, removing labels for peers that are no longer tracked. Gated on the `metrics` + `federation` features. (#564)
- **Differentiated Kubernetes health probes** — the metrics HTTP server now exposes three independent probe endpoints aligned with the Kubernetes startup/liveness/readiness model: `GET /health/live` returns 200 once the metrics server is reachable (failing probes restart the pod), `GET /health/ready` returns 200 only when the listener is bound and core subsystems have completed initial wiring (flips back to 503 during graceful shutdown so load balancers stop routing new traffic), and `GET /health/startup` returns 200 only after the accept loop has been entered (one-shot, never reset, allowing slow-starting pods extra grace before liveness/readiness begin in earnest). The legacy `/healthz` and `/readyz` paths remain as deprecated aliases for backwards compatibility. The bundled Helm chart is updated to use all three probes with sensible thresholds. (#562)
- **JetStream consumer lag metrics** — the NATS pull-consumer subscriber now polls `consumer.info()` every 5 seconds and forwards `num_pending`, `num_redelivered`, and `ack_floor.stream_seq` to a caller-supplied callback. Under `--features metrics,nats` these are exported as the gauges `rustgate_nats_consumer_pending`, `rustgate_nats_consumer_num_redelivered`, and `rustgate_nats_consumer_ack_floor_stream_seq`, plus the histogram `rustgate_nats_consumer_info_seconds` for per-poll latency, so operators can alert on cross-instance NATS bridge lag and redelivery storms. Transient `consumer.info()` errors are logged and retried on the next tick instead of killing the poller. The `rustgate-nats` crate stays Prometheus-free; the binary registers the metrics and wires the callbacks. (#565)
- **CoT archive retention and rotation** — operators no longer need an external `cron` job to keep `--archive-dir` bounded. Two new CLI flags configure retention: `--archive-max-size <bytes>` (env `RUSTGATE_ARCHIVE_MAX_SIZE`, default `0` = unlimited) caps total bytes across the archive directory and deletes the oldest files (by mtime) until the total drops below the cap; `--archive-max-age <seconds>` (env `RUSTGATE_ARCHIVE_MAX_AGE`, default `0` = unlimited) deletes files older than the configured age. A background task runs the rotation pass on a fixed interval, configurable via `--archive-rotate-interval` (env `RUSTGATE_ARCHIVE_ROTATE_INTERVAL`, default 60s). The currently active in-progress archive segment is excluded from both size accounting and deletion to avoid racing the writer. The new `rustgate_archive_bytes` Prometheus gauge (registered under `--features metrics`) reports the current total size of the archive directory after each pass. Both retention bounds default to disabled to preserve existing behavior. (#560)
- **Graceful connection drain on shutdown** — new `--shutdown-drain-timeout` CLI flag (env `RUSTGATE_SHUTDOWN_DRAIN_TIMEOUT`, default 10 seconds) bounds how long the server waits for in-flight queued messages to be flushed to clients during graceful shutdown. After listeners stop accepting on SIGTERM, the new `Router::close_all_session_senders` primitive drops every active session's outbound senders so each writer task observes a clean EOF after draining whatever is currently buffered in its priority and normal channels. The TLS, plaintext TCP, and WebSocket write loops were also fixed to keep draining the *other* channel when one of the two priority channels closes — previously a biased `tokio::select!` would `break` on the first `None`, silently dropping any messages still buffered on the other side at drain time. Setting the flag to `0` skips the drain phase and exits immediately. (#553)
- **Configurable enrollment CSR signing rate limit** — the enrollment server's per-IP CSR signing throttle is now exposed via the new `--enrollment-rate-limit` CLI flag (env `RUSTGATE_ENROLLMENT_RATE_LIMIT`, default 10 requests per source IP per minute). Rejected requests continue to return HTTP 429 with a `rate limit exceeded` body and emit a structured `rate_limit.triggered` audit event. A new `rustgate_enrollment_rate_limited_total` Prometheus counter is registered under `--features metrics` and incremented from a callback wired into `EnrollmentServer::with_rate_limit_callback`. Setting the flag to 0 disables the throttle (not recommended). (#552)
- **Hash-chained, tamper-evident audit log** — when `--audit-log <path>` is set, every audit record is now augmented with `prev_sha256` and `sha256` fields before being written. Each record's `sha256` is computed as `SHA-256(prev_hex_bytes || canonical_json_without_chain_fields)`, with the genesis record using 64 zero hex characters as `prev_sha256`. The chain transparently resumes across process restarts by reading the last line of the existing log. A new `rustgate verify-audit --file <path>` subcommand re-reads the file, recomputes the chain end-to-end, and exits non-zero on the first mismatch with a precise diagnostic (line number, expected vs actual hash). A small `write_anchor` helper writes the current chain tip to `<path>.anchor` so external systems can pin the chain on rotation. Tampering with any record in the middle of the file is now detectable. (#559)
- **Persistent de-identified access log** — new `--access-log` CLI flag (env `RUSTGATE_ACCESS_LOG`, `"-"` for stdout) opts into a per-message access log written as JSON lines to a dedicated sink. Implemented as a `tracing-subscriber` layer that filters `target="access"` events, mirroring the existing `--audit-log` plumbing. `Router::route` now emits one structured event per routed message with fields `src_cn`, `dst` (`direct:<sha256-cn-hash>` for unicast — the destination CN is hashed and truncated to 12 hex chars to avoid leaking PII — `group:<id>`, or `broadcast`), `msg_uid` (extracted from CoT XML payloads via a bounded scan, empty for non-CoT), `size`, `proto` (source transport), and `outcome` (`delivered`, `dedup`, or `expired`). Emission is gated behind `tracing::enabled!`, so when no access subscriber is attached the cost is a single O(1) filter check. (#558)

### Security

- **Audit log integrity** — operators can now prove that their audit log has not been silently edited or truncated by running `rustgate verify-audit --file <path>` against the configured `--audit-log` file. (#559)

- **Global admission control / backpressure** — new `--max-queued-bytes` CLI flag (env `RUSTGATE_MAX_QUEUED_BYTES`, default 512 MiB) caps the total in-flight routed bytes tracked across all sessions. When the counter crosses the high-water mark, the TLS accept loop is **deferred** (not errored) until the counter drops back below the low-water mark, which defaults to 90% of the high-water value and is overridable via `--max-queued-bytes-low-water`. Implemented as a shared `BackpressureGate` (AtomicUsize + `tokio::sync::Notify`) wired into `Router::route` via an RAII permit that releases its byte reservation on drop, making accounting panic-safe. Two new Prometheus metrics track the gate: `rustgate_queued_bytes` (gauge) and `rustgate_admission_deferred_total` (counter). Prevents a flood of slow readers from exhausting server memory on top of the existing per-session circuit breakers. (#551)
- **Per-client store-and-forward with bounded disk queue** — messages destined for a disconnected CN are now persisted to an embedded `redb` (MIT/Apache-2.0) database and drained on reconnect before live traffic resumes. Opt-in via the new `--client-queue-dir` CLI flag (env `RUSTGATE_CLIENT_QUEUE_DIR`); disabled by default, in which case offline messages continue to be dropped as before. A global byte cap configured via `--client-queue-max-bytes` (default 100 MiB, env `RUSTGATE_CLIENT_QUEUE_MAX_BYTES`) bounds total on-disk usage with drop-oldest FIFO eviction across all CNs. The queue survives server restarts: the in-memory index is rebuilt from the existing database on open. Prometheus metrics `rustgate_client_queue_depth`, `rustgate_client_queue_bytes` (gauges labelled by bucketed `identity_cn`), `rustgate_client_queue_drops_total`, and `rustgate_client_queue_drains_total` (counters) are registered under `--features metrics`, with CN label cardinality bounded by the existing `--metrics-identity-allowlist` mechanism. (#548)
- **Cross-path message deduplication** — new `--dedup-window-secs` CLI flag (env `RUSTGATE_DEDUP_WINDOW_SECS`, default 0 = disabled) enables a router-level LRU dedup cache keyed by `SHA-256(uid || 0x00 || time_le || 0x00 || payload)`. When the same logical message arrives via multiple ingress paths (e.g. a direct client and a federation peer that forwarded it) within the configured window, the router suppresses duplicates before dispatch so subscribers receive each message exactly once. For CoT XML the `uid` attribute is extracted from the payload; for non-CoT payloads (protobuf, raw binary) `uid` is empty and the key degenerates to a pure content hash, so byte-identical protobuf/binary payloads are deduped as well. The cache size is bounded via `--dedup-cache-size` (env `RUSTGATE_DEDUP_CACHE_SIZE`, default 100000); evictions follow LRU order, and entries older than the window are lazily replaced on lookup. Suppressed duplicates are counted by the new `rustgate_dedup_hits_total` Prometheus counter, and current occupancy is exposed via `rustgate_dedup_cache_size`. Because the full payload is folded into the hash, messages sharing a `uid` but with different bytes are treated as distinct. Disabled by default to preserve existing behavior. (#549)
- **`rustgate-client` reference crate** — new workspace member providing an ergonomic client API on top of the existing `rustgate-transport` codecs. Exposes `Client::connect`, `Client::send`, `Client::subscribe`, and `Client::disconnect`, plus a `ClientConfig` builder with mTLS PEM file/byte sources, codec selection, plaintext fallback for tests, optional connect timeout, and opt-in auto-reconnect with exponential backoff (100 ms → 30 s, configurable max attempts). Reuses `FramedCodec` from the transport crate so client and server cannot drift. Includes an `examples/echo.rs` reference echo client and replaces ad-hoc TLS bring-up in two transport integration tests. (#550)
- **TOML configuration file support** — new `--config <path>` CLI flag (env `RUSTGATE_CONFIG`) loads a TOML file whose keys mirror the existing CLI flag names (kebab-case). Settings are merged in the order **defaults → file → environment variables → CLI flags**, so command-line arguments and environment variables always override file values. Two new utility subcommands ship alongside the flag: `rustgate print-config` writes the effective merged configuration as TOML to stdout, and `rustgate validate-config` parses the file (rejecting unknown keys and missing required fields) and exits non-zero on error. The config file is loaded via the `figment` crate (Apache-2.0/MIT) with the TOML provider; running the server with no subcommand continues to start the listener as before. (#547)
- **OCSP stapling for server certificates** — new `ocsp` feature flag adds OCSP response stapling to the TLS handshake using the `ocsp-stapler` crate (MPL-2.0). When enabled with `--ocsp-stapling` (env `RUSTGATE_OCSP_STAPLING`), the server's certificate resolver is wrapped with `ocsp_stapler::Stapler`, which fetches OCSP responses for the active certificate in a background tokio task and attaches them to the handshake so clients can verify revocation status without contacting the issuing CA. Coexists with the existing CRL-based client certificate verification (the two operate on opposite sides of the handshake). Most useful with enterprise/private CAs that operate their own OCSP responder; Let's Encrypt dropped OCSP support in 2025. The first handshakes after startup may be served without a stapled response until the background fetcher completes its initial cycle. The stapler is gracefully stopped during shutdown. (#524)
- **Per-identity Prometheus metrics with bounded cardinality** — `rustgate_messages_routed_total` and `rustgate_messages_dropped_total` now carry an `identity_cn` label so operators can attribute routing volume and rate-limit drops to individual clients. Cardinality is bounded by an optional CN allowlist loaded from `--metrics-identity-allowlist` (env `RUSTGATE_METRICS_IDENTITY_ALLOWLIST`, one CN per line, `#` comments allowed); CNs not in the allowlist — and **all** CNs when the allowlist is unset — collapse into the literal `"other"` bucket, capping per-identity cardinality at 1 by default. New `--metrics-per-identity` flag (env `RUSTGATE_METRICS_PER_IDENTITY`, default false) opt-in registers Tier 2 per-identity metrics: `rustgate_per_identity_handshake_failures_total`, `rustgate_per_identity_session_duration_seconds`, `rustgate_per_identity_bytes_sent_total`, and `rustgate_per_identity_bytes_received_total`. Tier 2 metrics are not registered when the flag is disabled, imposing zero overhead. (#526)
- **SIGHUP config reload** — on Unix, sending `SIGHUP` to the running server now reloads the server certificate (via the existing `CertReloader`), the group ACL policy (via the existing `AclReloader`), and re-validates the configured CRL file from disk. Each component is reloaded independently — failures in one do not abort the others — and structured `target="audit", event_type="config.reload"` events are emitted per component with `result=success|failure`. SIGHUP reload is Unix-only; on other platforms the handler is not installed. CRL reload re-parses and freshness-checks the file but does not yet swap CRLs into the live TLS listener; applying CRL changes to in-flight handshakes still requires a server restart. (#528)
- **ACL REST API authentication** — new `--acl-api-token-file` CLI flag (env `RUSTGATE_ACL_API_TOKEN_FILE`) guards the `/api/acl/` endpoints with a bearer token. When unset, the ACL API is not registered at all and `/api/acl/` requests fall through to 404. When set, every request must present `Authorization: Bearer <token>` and the token is compared in constant time. Mutations (`PUT`/`DELETE`) are now persisted atomically to the configured `--group-acl-file` (write-to-tmp + fsync + rename) and the hot reloader's cached hash is updated so the next poll does not re-detect the change. Group identifiers are validated against a strict `[A-Za-z0-9_.:-]{1,128}` allow list. (#538)
- **JSON audit log sink** — new `--audit-log` CLI flag (env `RUSTGATE_AUDIT_LOG`) writes audit events as JSON lines to a dedicated file, separate from the main log stream. Filters only `target="audit"` events using a per-layer `Targets` filter. Use `"-"` for stdout. Audit events now include `session_id` on connect/disconnect for correlation. (#525)
- **ACL deny rules** — `GroupAcl` now supports optional `deny_send` and `deny_receive` lists alongside the existing allow lists. Deny is evaluated first and overrides allow, enabling fine-grained block-list semantics: a CN appearing in a deny list cannot send/receive even when also in the allow list. With an empty allow list, the deny list acts as a pure block list (the group is open except for denied CNs). Legacy ACL JSON files without `deny_send`/`deny_receive` continue to parse unchanged. (#523)
- **ACL management REST API** — new `/api/acl/` endpoints exposed on the metrics HTTP server (mirrors the `/api/federation/` pattern). Supports `GET /api/acl/groups` to list current rules, `PUT /api/acl/groups/{group}` to upsert an entry, `DELETE /api/acl/groups/{group}` to remove one, and `POST /api/acl/reload` to re-read the on-disk ACL file. Mutations rebuild the full policy and atomically swap it on the router via `ArcSwap`. (#522)
- **Hot-reloadable ACL** — the group access control policy can now be updated at runtime without restarting the server. The router's ACL is stored in an `ArcSwap` for lock-free reads, and a new `--acl-reload-interval` CLI flag (env `RUSTGATE_ACL_RELOAD_INTERVAL`, default 0 = disabled) enables periodic polling of the `--group-acl-file` for changes. File changes are detected via SHA-256 hash comparison; only modified files trigger a policy swap. Audit events are emitted on reload success and failure. (#521)
- **Message priority channels** — replaced the single per-session mpsc channel with a dual-channel approach: a high-priority channel (capacity 16) for Position and Alert messages, and a normal-priority channel (capacity 64) for all other message types. Write loops use biased `tokio::select!` to always drain priority messages first, ensuring time-sensitive situational awareness data is delivered ahead of bulk traffic. The circuit breaker applies across both channels. (#519)

### Fixed

- **Store-and-forward ordering, async safety, and naming** — several correctness bugs in the per-client store-and-forward queue (#548): (1) the reconnect sequence now drains the offline queue **before** registering the session with the router, so live traffic routed mid-handshake can no longer slip ahead of queued messages (FIFO across the reconnect boundary is now strict across TLS, plaintext TCP, and WebSocket transports); (2) `ClientQueue::enqueue` no longer performs `redb::begin_write` + `commit` on the async router worker — persistence is handed off via a bounded `tokio::sync::mpsc` channel to a dedicated writer task that commits inside `spawn_blocking`, with a new `rustgate_client_queue_writer_drops_total` counter for overflow; (3) `peek_cn` was renamed to `peek_dest_cn` with corrected docs, and on reopen non-direct (broadcast/group) entries are now skipped and counted via `rustgate_client_queue_skipped_unsupported_total` rather than warned as malformed; (4) TTL is now enforced on drain, skipping expired entries and incrementing `rustgate_client_queue_expired_total`; (5) new `rustgate_client_queue_enqueues_total` counter surfaces the offline write rate; (6) the router's `send_to_session` failure log was corrected from "session channel full or disconnected" to "session channel closed" since `tokio::mpsc::Sender::send().await` only errors on receiver close.

### Changed

- **GroupAcl default semantics restored** — an ACL entry with an empty allow list and empty deny list again denies all sends and receives, matching the pre-deny behavior. The deny-rule extension (#523) accidentally flipped the empty allow list to mean "open", which silently relaxed existing policies. Block-list mode (empty allow, non-empty deny) is unchanged. (#538)
- **Audit log append mode** — the `--audit-log` file is now opened with create+append instead of truncated, preserving existing audit events across restarts. (#538)
