### Added

- **Unit-test coverage for `rustgate-transport` TLS listener** — `crates/rustgate-transport/src/listener.rs` owns every server-side wiring site's first line of defence — the async `bind` / `bind_with_handshake_limit` entry points, the `DEFAULT_MAX_HANDSHAKES = 100` constant operators size tactical deployments against, the `local_addr()` discovery method every integration test depends on, the `set_on_handshake_error` callback slot the metrics layer wires into, and the custom `Debug` impl that `tracing::info!(?listener, …)` and `tracing::debug!(?listener, …)` render on startup and inside the accept loop — but had zero inline tests; integration-test coverage (`tls_listener.rs`, `crl.rs`, `tls_security.rs`, `pq_kex.rs`) all drive the accept loop end-to-end and so conflate listener construction with handshake and identity extraction. Issue #909 flagged the file as a critical-path gap because a regression in the listener's Debug impl would silently leak the `TlsAcceptor` (and with it the server-cert handle) into operator logs, and a regression in the `DEFAULT_MAX_HANDSHAKES` default would silently change every production deployment's DoS posture. The new `#[cfg(test)] mod tests` adds 14 tests behind a shared `test_tls_config()` helper that installs the rustls default crypto provider idempotently and builds a `TlsConfig` from a fresh `TestCa` — no handshake is ever completed, so the tests stay fast (under 20 ms total) and do not duplicate integration-test territory. Pinned invariants: (a) `DEFAULT_MAX_HANDSHAKES` is exactly `100` — a silent change shows up as a test diff instead of a production capacity surprise; (b) `bind` succeeds on `127.0.0.1:0` and `local_addr()` reports a non-zero ephemeral port on a loopback IP (the two surfaces every test harness depends on); (c) `bind` wires the default limit through to the semaphore — the `max_concurrent_handshakes` field in the Debug output equals `DEFAULT_MAX_HANDSHAKES`, proving the default path has not been rerouted to a magic number; (d) `bind_with_handshake_limit` honours a custom value (tested at both `42` and the boundary `1` for single-permit serialization use-cases); (e) two listeners bound to `127.0.0.1:0` coexist on distinct ephemeral ports so the per-listener accept loop is not accidentally sharing a socket; (f) the `map_err` wrap on the underlying `TcpListener::bind` failure surfaces as a `TransportError::Other` carrying the `"failed to bind TLS listener"` context prefix — exercised by holding a `std::net::TcpListener` on the target port and confirming the second bind fails with that prefix in the error string, so operators keep their triage signal on EADDRINUSE and similar kernel-side bind failures; (g) the Debug impl renders the `TlsListener` type name, embeds the concrete bound port value, keeps the `max_concurrent_handshakes` field visible, and — critically for secret hygiene — renders the `tls_acceptor` field as the fixed `"<TlsAcceptor>"` sentinel rather than letting `TlsAcceptor`'s own Debug leak the server's `ServerConfig` (and thus the server-cert handle) into logs; (h) `set_on_handshake_error` accepts an `OnHandshakeError` callback and overwrites cleanly on a second install (Option-based storage, not append-vec — a future refactor that silently doubled callback fire would fail the second-install case); and (i) a compile-time assertion that `TlsListener: Debug` survives so every `tracing::info!(?listener, …)` site keeps producing useful output at the type level. No behavioural change — all changes are additive test code. (Refs #909)
- **Unit-test coverage for `rustgate-core::message` routing contracts** — `crates/rustgate-core/src/message.rs` carries the envelope types (`RoutableMessage`, `Metadata`, `Destination`, `MessageType`) that every inbound message is normalised into before the router sees it, plus the `SOURCE_FEDERATION` and `SOURCE_MAVLINK` wire tags downstream audit/echo-prevention filters key off. The pre-existing inline test module covered only three cases (`MessageType` Display, `Destination` Display for Group/Broadcast/Direct, and the `SOURCE_MAVLINK` constant), leaving four documented contracts pinned nowhere: `Metadata::is_expired`'s clock-skew tolerance, `Destination::kind_str`'s Prometheus-label stability, `Destination::Display` for the `Multicast` variant, and the `SOURCE_FEDERATION` constant. Eleven new tests close the gap. `metadata_is_expired_none_ttl_never_expires`, `metadata_is_expired_past_ttl_is_true`, and `metadata_is_expired_within_ttl_is_false` pin the three ordinary TTL branches — the doc comment explicitly promises that a `None` TTL never expires (federated control traffic relies on this to avoid silently falling out of the position cache) and a regression that flipped the default would be silent otherwise. `metadata_is_expired_future_received_at_treated_as_fresh` pins the clock-skew branch: when `SystemTime::now().elapsed_since(received_at)` returns `Err` because `received_at` is in the future (another node's clock ran ahead), the contract is to treat the message as fresh rather than drop it; a well-intentioned "strictness" refactor that changed the `Err(_) => false` arm to `Err(_) => true` would immediately break federated delivery in any deployment with >0 ms of clock drift. `destination_kind_str_is_low_cardinality_label` pins all four variant strings (`"group"`, `"direct"`, `"broadcast"`, `"multicast"`) — these are both Prometheus label values (where high cardinality is a metrics-backend outage) and SIEM grep tokens (where a rename silently breaks every deployed alerting rule), and the doc comment explicitly calls them "stable across releases". `destination_kind_str_returns_static_str` pins the `&'static str` return type via a compile-time type ascription so a future refactor to an allocating path (e.g. `String`) that would force an allocation on every routed message cannot land silently. `destination_display_multicast_joins_groups_with_commas` and `destination_display_multicast_empty_list` pin the Multicast variant of the Display impl, which the pre-existing tests missed entirely — operators grep for `multicast:[group-name]` substrings in audit output, so the bracket + comma-separated format is a load-bearing contract. `source_federation_constant_is_stable` pins the `"federation"` string value parallel to the existing `SOURCE_MAVLINK` test — this constant is documented in CLAUDE.md's shared-infrastructure table as the authoritative tag for federated messages. `message_type_display_other_preserves_payload` pins the `Other(String)` edge cases (empty inner, punctuation-rich inner) against accidental sanitisation. `message_type_equality_includes_inner_string` pins the derived `PartialEq` semantics on the `Other(String)` variant so a routing path that keys off `MessageType` equality cannot silently collapse two distinct `Other` types. Refs #909.
- **Gap-coverage tests for `rustgate-core::b64` encode/decode helpers** — `crates/rustgate-core/src/b64.rs` is the workspace's single entrypoint for base64 (17+ downstream callers per #830) and backs two cryptographically-sensitive call sites: HMAC digest exchange on the HTTP publisher and JWT header/payload encoding on the federation path. The pre-existing four tests covered the sunny-day round-trips and the §4-alphabet-rejects-§5 direction of engine separation, leaving six observable contracts unpinned where a refactor could silently corrupt callers. Nine new tests close the gaps: `empty_input_round_trips_on_standard_engine` and `empty_input_round_trips_on_url_safe_engine` pin that a zero-length input encodes to an empty string and decodes to an empty `Vec<u8>` — silent emission of stray bytes on empty input would contaminate HMAC digests whose payload is a legitimate empty blob and fabricate JWT parts that look syntactically valid. `decode_rejects_non_alphabet_bytes_with_decode_error` binds the returned error to `DecodeError` to prove the type re-export remains part of the module's public surface — callers in `enrollment/auth.rs` and `federation/jwt.rs` propagate this type through their own error enums with `?`, and a future change that hid the re-export would force every downstream crate to add `base64` as a direct dependency. `decode_url_safe_rejects_standard_padded_output` mirrors the existing `standard_rejects_url_safe_alphabet` test in the reverse direction — `URL_SAFE_NO_PAD` must refuse a canonically-padded blob — so the engine pair is strictly mirrored and a caller cannot accidentally feed a JSON-shaped blob into the JWT decoder and have it silently succeed. `url_safe_rejects_plus_and_slash_alphabet` exercises bytes that produce `+`/`/` under §4 and asserts `URL_SAFE_NO_PAD` rejects them, defending against an engine swap that would silently decode the wrong alphabet. `encode_accepts_all_as_ref_byteslike_types` pins the generic `T: AsRef<[u8]>` bound across every call shape actually used across the 17 downstream crates (slice, array, `&Vec<u8>`, `&String`, `&str`), so a refactor narrowing the bound to `&[u8]` would break callers before CI rather than after release. `large_binary_round_trips_across_chunk_boundaries` round-trips 3 KiB of deterministic binary through both engines — exercising many §4 3-byte-group boundaries past the typical stack-buffer threshold — so a chunking regression surfaces here even when the tiny happy-path round-trips still pass. `standard_engine_produces_padded_output_with_equals` and `url_safe_engine_never_emits_padding` pin the padding contracts at the three length-mod-3 boundaries (1-byte → `==`, 2-byte → `=`, 3-byte → none; URL-safe → never), so snapshot tests and wire fixtures that rely on the exact string shape continue to match after an engine-config change. All tests operate on in-memory buffers — no network, no filesystem, no feature gating — and add zero runtime to the test binary (the existing `rustgate-core` library suite still runs 150 tests in ~1.7s). Refs #909.

- **Unit-test coverage for `rustgate-http` SSRF-safe DNS resolver** — `crates/rustgate-http/src/resolver.rs` is the runtime half of the SSRF defence-in-depth pair: `config.rs` validates the URL at load time (covered extensively by 35+ inline tests), and `SsrfSafeResolver` re-checks the resolved IP addresses at connection time to close the DNS-rebinding TOCTOU gap. An attacker who controls a hostname whose `A`/`AAAA` record initially pointed at a public IP (passing config validation) but flips to `127.0.0.1` or `169.254.169.254` by the time the first HTTP request fires would previously have slipped through unnoticed; only the runtime filter in `resolver.rs` catches that flip, and prior to this PR that file had zero coverage. Seven new inline tests pin the full observable contract: `new_preserves_allow_private_true` and `new_preserves_allow_private_false` pin that the constructor stores the flag both ways (a regression here silently neutralises either the test-fixture escape hatch or the production filter); `resolve_rejects_localhost_by_default` exercises the production path end-to-end — `/etc/hosts` resolves `localhost` to `127.0.0.1`, the resolver filters it, and the returned error carries the three operator-grep-grade tokens `"SSRF protection"`, `"private/reserved"`, and `"localhost"`; `resolve_rejection_surfaces_as_permission_denied` downcasts the boxed error to `std::io::Error` and asserts `ErrorKind::PermissionDenied` so a future refactor cannot silently swap it for `InvalidData` and change retry/circuit-breaker classification; `resolve_allows_localhost_when_escape_hatch_set` pins that `allow_private = true` lets the integration-test wiring reach `127.0.0.1` and every yielded address is actually loopback; `resolve_propagates_dns_failure_without_wrapping` uses the RFC 6761 §6.4-reserved `.invalid` TLD — guaranteed to never resolve on any host — to assert that a pure DNS failure does not get relabelled as an SSRF rejection, so callers can distinguish "name does not exist" from "name resolves to a blocked IP"; `resolve_escape_hatch_does_not_filter_public_hostnames` uses `.invalid` under `allow_private = true` to pin that the escape hatch is a pure pass-through, not a loopback-only special case, and must never inject its own rejection on the allow path. All tests use `reqwest::dns::Name::from_str` for input construction (the only public constructor) and `tokio::net::lookup_host` for DNS resolution; no network egress required — `localhost` resolves via `/etc/hosts` and `.invalid` fails at the resolver stub. Refs #909.

### Fixed

- **Backpressure gate no longer oscillates at the high-water boundary; hot-path callbacks must be non-blocking** — `rustgate_transport::BackpressureGate` now requires the in-flight byte counter to stay at or below `low_water` continuously for at least `resume_dwell` (default **1 second**) before admission resumes after a block. Previously, any drop to `low_water - 1` immediately cleared `blocking` and woke the accept loop, so a workload that hovered between `low_water + 1` and `low_water - 1` (e.g. one slow client feeding an evenly-sized fan-out) would flip admission on and off at the cadence of the TCP handshake loop — each new session's first message pushed the counter back over `high_water`, the permit drop dipped it under `low_water`, and the thrashing wasted CPU, spammed the `admission_deferred_total` metric, and could starve the server's per-host handshake-parallelism budget. The fix is an atomic `AtomicU64` cooldown timestamp (`below_low_since`, relative to a per-gate `tokio::time::Instant` epoch so `start_paused` tests stay deterministic under the virtual clock) that (a) arms on the first `sub` that drops the counter to or below `low_water` while blocking, (b) clears on any subsequent `add` that pushes back above `low_water`, and (c) is read by both `sub` and a new 100ms poll branch inside `wait_for_capacity` so dwell expiry can release the accept loop even when no further `sub` arrives. The hot path remains lock-free: `sub` short-circuits the dwell bookkeeping entirely when the gate is not blocking. A new `--backpressure-resume-dwell-ms` CLI flag (env `RUSTGATE_BACKPRESSURE_RESUME_DWELL_MS`, default 1000) lets operators tune the dwell — setting `0` restores pre-fix behaviour for bursty-but-not-oscillatory workloads where the latency cost matters. Separately, the `OnDeferred` and `OnBytesChanged` callback type docs now explicitly require non-blocking bodies: the gauge/counter update path fires on every byte-count change (i.e. potentially once per message), and `wait_for_capacity` is awaited on the TLS accept loop — a blocking callback there stalls the entire accept path and breaks admission control. Six new regression tests using `#[tokio::test(start_paused = true)]` + `tokio::time::advance` cover: default dwell keeps the gate blocked until the timer elapses, oscillation at the boundary cancels the in-flight cooldown, `wait_for_capacity` wakes via the internal poll without any external `sub`, a re-cross above `high_water` resets the dwell window, explicit `Duration::ZERO` preserves the legacy immediate-resume behaviour byte-for-byte, and the `Debug` impl surfaces the new field so operator log greps see it. (#878)
- **Gate `TestNatsServer::start()` on JetStream readiness, not just TCP `INFO` greeting** — `rustgate-test-utils`'s `TestNatsServer::try_start` previously returned as soon as the spawned `nats-server` subprocess replied to the NATS protocol `INFO` greeting, but `nats-server --jetstream` binds its TCP listener well before the JetStream subsystem finishes initialising and the meta-leader is elected. On a loaded runner the gap between "TCP accepts connections" and "JS API accepts requests" exceeds the 5s per-operation JetStream timeout, so any test that calls `jetstream.create_key_value(…)` (or `create_stream`, `create_consumer`, …) on the context returned from `TestNatsServer::jetstream()` flakes with `JetStream error: timed out` on the very first call. The symptom observed in CI was `create cm_b: failed to create federation-claims KV bucket` in `rustgate-federation::ha_integration::claim_gates_peer_connection`, but every one of the 14 `ha_integration.rs` tests and every current or future NATS-backed test in the workspace is exposed to the same race. `try_start` now chains a second readiness probe after the `INFO` greeting succeeds: a throwaway `async_nats::connect` + `jetstream::new` + `query_account` round-trip that maps to `$JS.API.ACCOUNT.INFO`, which only returns `Ok` once the JS meta-leader has been elected. The probe is bounded by the existing `READY_TIMEOUT` deadline so a genuinely broken JetStream configuration still fails fast, and its connection is dropped before `start()` returns so callers always hold a fresh client created through `TestNatsServer::jetstream()`. A new unit test in `test_utils::nats::tests` — `start_completes_only_after_jetstream_accepts_kv_create` — pins the invariant by creating a KV bucket and round-tripping a `put`/`get` immediately after `start()` returns, with no retry loop around the KV call. Also enables the async-nats `kv` feature on `rustgate-test-utils` so the regression test can construct a KV config without dragging in a parallel feature flag. (Fixes the flake that broke #976's CI on 2026-04-19.)
- **Relax PQ kx-group assertions so FIPS-plus-post-quantum CI stops reporting spurious failures** — `crates/rustgate-transport/tests/pq_kex.rs` had two assertions that were correct for the single-feature `post-quantum` build but deterministically failed under the CI command `cargo nextest run -p rustgate-transport --features proto,fips,post-quantum,ocsp,spiffe`: `pq_provider_includes_mlkem_groups` required `X25519` in `aws_lc_rs::default_provider().kx_groups`, and `pq_classical_client_falls_back_to_x25519` required the negotiated group between a ring-backed client and the PQ-backed server to be exactly `X25519`. When `rustls/fips` is active, `default_provider()` is restricted to FIPS-approved groups — `X25519MLKEM768` and the NIST curves `secp256r1/384r1/521r1` — and drops `X25519`, which is not FIPS-approved. The original issue (#957) framed this as a multi-test race against the process-global `CryptoProvider`, but the failure reproduces in isolation and repeats deterministically across runs: there is no race, it is a feature-combination mismatch. The provider-shape test now asserts the invariant we actually care about — "hybrid PQ is offered *and* at least one classical group remains negotiable" — accepting any of `X25519`, `secp256r1`, `secp384r1`, or `secp521r1` as the classical fallback. The negotiation test now asserts the negotiated group is *some* classical (non-PQ) group, because the correctness condition for "graceful fallback from a ring-only client" is "non-PQ group was chosen", not the specific identity of that group; FIPS forces the pair onto `secp256r1` where non-FIPS lands on `X25519`, and both outcomes are correct fallbacks. Verified by running the file under both feature sets: `--features post-quantum` → 8/8 pass, `--features proto,fips,post-quantum,ocsp,spiffe` → 8/8 pass. (#957)

### Security

- **Migrate HTTP-egress `pin-sha256` to RFC 7469 SPKI pinning** — `rustgate_http::pinning::PinnedCertVerifier` now computes `SHA-256(SubjectPublicKeyInfo DER)` on the leaf certificate and compares against the configured pins, rather than hashing the entire leaf DER. The old full-DER semantic was out of step with every mainstream pinning tool: Chromium, Mozilla, the RFC 7469 / HPKP `report-uri` ecosystem, and the standard OpenSSL pin recipe (`openssl x509 -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64`) all hash SPKI. Operators generating pins from any of those sources would silently fail-closed against a rustgate binary because the pin in their config file matched the public key, not the whole cert. Worse, the previous behaviour actively punished good DevOps hygiene: a same-key cert rotation (fresh serial, fresh validity window, fresh SAN list, but the long-lived key material preserved) mutates the leaf DER and therefore mutated every deployed full-DER pin — every annual cert roll on every edge became a flag-day config push, with the inevitable result that tired operators just widened `pin-sha256` to an empty list and quietly turned off defense-in-depth. SPKI pinning inverts that: the pin survives same-key rotation and only breaks on the security-relevant event of a real key change, which is when an operator *does* want to know. The module-level docs in `crates/rustgate-http/src/pinning.rs`, the `TlsConfig::pin_sha256` field doc in `config.rs`, and the `docs/http-egress.md` Certificate Pinning section all document the RFC 7469 semantic and embed the canonical OpenSSL generation recipe. A new private `extract_spki_der` helper fails closed on a malformed cert via `TlsError::General("certificate SPKI extraction failed: …")` rather than panicking or silently admitting the connection, and is shared between the verifier hot path and a test-only `spki_pin` helper so the pin computation cannot drift between production and test fixtures. New `rustgate_test_utils::certs::generate_server_keypair` plus `TestCa::issue_server_cert_with_key(&KeyPair, cn, sans)` let tests model the same-key-different-cert flow; the existing `issue_server_cert` is refactored to delegate to the new helper so single-call usage is unchanged. Five new regression tests in `pinning::tests` pin the full observable contract: `distinct_keypairs_hash_to_distinct_spki_pins` (independent keys yield independent pins — the core key-sensitivity property that keeps a CA-compromise attacker from swapping the leaf), `spki_pin_survives_same_key_reissue` (the direct #948 regression guard — asserts reissued leaf DERs differ but SPKI bytes and SPKI pins stay identical), `verifier_accepts_matching_spki_pin_from_real_cert` (round-trips a real issued cert's pin through `b64::encode` → `parse_pins` to mirror config-file ingestion and confirm the verifier's hot path and the config loader compute the same 32 bytes), `legacy_full_der_pin_no_longer_matches` (a pre-#948 full-DER pin must not collide with the new SPKI pin for the same cert — silent acceptance would defeat the whole migration), and `extract_spki_der_rejects_malformed_cert` (the helper surfaces an x509-parser error as a `TlsError::General` so the handshake path fails closed on a malformed cert, not on a panic). **Breaking change for operators:** existing full-DER pins from pre-#948 deployments will stop matching on upgrade; regenerate each pin with the OpenSSL recipe in `docs/http-egress.md` or the module docs. A rolling upgrade can overlap both forms by running the old and new pin simultaneously across a canary window, since both are independent 32-byte base64 strings and the pin array is OR-matched. (Closes #948)
- **Guard release-artifact filenames against co-packaging collisions (F-21)** — `release-binary.yml` builds six archives from a 2×3 matrix (x86_64/aarch64 × base/fips/pq) and the "Package binary" shell step names each one `rustgate[-fips|-pq]-${VERSION}-${TARGET}.tar.gz`. The distinct discriminators (`fips`, `pq`, or unmarked) were correct as of today but the workflow had no structural guard against a future matrix edit silently producing two entries that compute the same archive name — `gh release upload --clobber` would then overwrite one with the other, the cosign signature and build-provenance attestation would be bound to whichever variant wrote last, and downstream `cosign verify-blob` consumers would admit a binary under the wrong identity. A new `scripts/check-release-artifact-names.py` parses `.github/workflows/release-binary.yml`, re-implements the Package-binary naming logic against each matrix entry, and asserts three invariants: (1) every entry produces a distinct archive filename, (2) each non-base entry carries its discriminator token (`-fips-` / `-pq-`) in the filename while the base build carries neither, and (3) every filename matches the shape `rustgate-[fips-|pq-]<version>-<target>.tar.gz`. A `fips=true + pq=true` combination is explicitly rejected as a misconfiguration (the workflow's `if/elif` would silently pick `fips`, making the `pq=true` flag a dead marker). The script runs in the existing `playbook-lint` CI job on every PR — not only those touching the workflow — so a rename in an unrelated helper that the workflow references surfaces before a release tag cuts in, and uses the standard `::error file=…::` annotation format so the GitHub UI highlights the offending line. Closes the F-21 caveat from the residual-findings audit (#887). The F-21 primary advisory (aws-lc-sys VEX entry, RUSTSEC-2026-0049) was already resolved in #777 — this PR closes the forward-looking "don't accidentally co-package" half that was deferred to a separate ticket. (#887)
- **Harden encrypted-archive writer against symlink TOCTOU and ChaCha20-Poly1305 nonce reuse** — `rustgate_core::encrypted::EncryptedWriter::create` now opens the target file with `O_NOFOLLOW` on Unix (via `OpenOptionsExt::custom_flags` with a platform-pinned `O_NOFOLLOW` constant), translating the kernel's `ELOOP`/`EMLINK` refusal into a new `EncryptError::SymlinkTarget { path }` variant. On a multi-tenant host an attacker who can plant a symlink at the archive path (store-forward queue, encrypted audit log) could previously redirect our `truncate + write` into any file the service account can open, silently overwriting unrelated data; `O_NOFOLLOW` is the atomic TOCTOU-free defense and intermediate components are still followed, matching the scope of the threat. A regression test plants a sensitive file under a symlink at the target path and asserts both that `create()` returns `SymlinkTarget` and that the sensitive file's contents survive untouched. Separately, the 32-bit per-file chunk counter used for nonce derivation — `nonce = base_nonce (8 bytes) || counter_be (4 bytes)` — had a reuse window at exhaustion: the old `write_chunk` / `finish` path incremented `counter` via `checked_add(1)` *after* sealing and persisting the chunk, so when `counter == u32::MAX` the ciphertext with nonce `(base, u32::MAX)` landed on disk, the increment errored, and `counter` stayed pinned at `u32::MAX`. A caller that ignored the `CounterOverflow` error (or subsequently called `finish()`) would re-seal under the same nonce — catastrophic for ChaCha20-Poly1305. Both methods now reserve the post-increment *before* computing the nonce and performing the AEAD seal, so refusal is atomic: if we cannot advance, we do not write. A new regression test sets the counter to `u32::MAX`, confirms `write_chunk` returns `CounterOverflow` without appending any bytes, confirms the counter is not silently wrapped, confirms a follow-up `finish()` also refuses, and confirms the resulting file — intentionally missing a terminator — is rejected by `decrypt_file` as `Truncated` so operators are forced to rotate the key or file instead of trusting a half-sealed archive. (#809)
- **Persist audit-chain tip across restarts for cross-boot tamper detection** — `rustgate_core::audit_chain` gains an explicit `<audit.jsonl>.anchor` sidecar file that pins the SHA-256 tip of the hash-chained audit log on clean shutdown and lets the next boot prove the chain was not tampered with while the service was down. `HashChainWriter` gains `with_tip_observer(Arc<ArcSwap<String>>)`: the writer atomically publishes its current chain tip on every chain advance, so shutdown code owning the observer can snapshot the latest hash even though the writer itself is hidden inside a `Mutex<Box<dyn Write>>` owned by the `tracing` subscriber. A new `check_chain_continuity(path) -> ChainContinuity` function reads the live tail hash via the existing torn-write-tolerant `read_chain_tip` helper and compares it to the persisted anchor, returning `NoAnchor` (fresh install — benign, no previous shutdown to match), `Match { tip }` (anchor agrees with live tip — clean restart, no tampering), or `Mismatch { anchor_tip, live_tip }` (anchor disagrees — the log was truncated, extended, or rewritten while the service was stopped). The `rustgate-server` binary wires all three pieces end-to-end: on startup it runs the continuity check against the configured `--audit-file` (plain-file path only; the rotating appender path is left for a follow-up), and on `Mismatch` it bails via `anyhow::bail!` so a hostile actor cannot silently edit the log offline and have the next boot continue the chain from the forged tip. Operators needing a one-shot escape hatch — e.g. intentional log rotation outside the service's lifecycle, or a manual archival operation that updates the tail — opt in via the new `--audit-allow-chain-break` flag (env `RUSTGATE_AUDIT_ALLOW_CHAIN_BREAK`, defaults `false`), which downgrades the break from fatal to audited: the new `audit::chain_discontinuity(audit_path, anchor_tip, live_tip, action, reason)` event is emitted after the tracing subscriber comes up, so the break is itself recorded as a cryptographically chained audit record from the new live tip forward. On graceful shutdown, the server snapshots the observed tip, calls `write_anchor`, and emits either `audit::chain_anchor_persisted` or `audit::chain_anchor_persist_failed` depending on whether the sidecar file was written. Ten new unit tests in `audit_chain.rs` cover the anchor write/read round-trip, malformed/truncated anchor payloads, the continuity verdicts (no anchor, match, mismatch against post-anchor extension, mismatch against post-anchor truncation), observer updates on chain advance, and a full end-to-end lifecycle test that models the production path: writer → observer snapshot → anchor write → next-boot continuity check returns `Match`. Two new CLI tests pin the default-false posture of `--audit-allow-chain-break` and its opt-in behaviour. (#718)
- **Tenant-isolated cross-path dedup cache** — `rustgate_transport::DedupCache` now folds the sender's tenant (derived from the client cert's X.509 Organization field, exposed via `Identity.tenant`) into the SHA-256 key preimage alongside the existing `uid || 0x00 || time_le || 0x00 || payload` slots. Previously a message sent by tenant `A` could suppress a byte-identical message sent by tenant `B`, opening a timing side-channel where a malicious tenant could probe for the existence of specific messages in another tenant by submitting candidate `(uid, time, payload)` triples and observing whether delivery succeeded (= the other tenant did not send this) or was silently deduplicated (= the other tenant sent exactly this). - **Persist the CRL `crlNumber` counter across enrollment-server restarts** — `rustgate_enrollment::RevocationStore` previously held the CRL serial in a `static AtomicU64` initialised to `1` at process start, so every restart re-issued a CRL with `crlNumber = 1`. RFC 5280 §5.2.3 requires the `crlNumber` extension to increase monotonically for each CRL issued by a given CA, and x509 verifiers that enforce this (OpenSSL's `X509_CRL_get_ext_d2i(…, NID_crl_number)` path among them) will reject a restarted-CA's CRL as a replay of a prior one — locking clients into stale revocation state until their cached CRL expires, or hard-failing verification depending on verifier posture. When no prior counter is on disk (fresh install, lost state file, or a legacy document), the in-memory counter seeds from `wall_clock_fallback_serial` (UNIX milliseconds) so the next `crlNumber` exceeds any plausible small-integer serial an older build would have issued — preserving monotonicity even across state loss. A hand-crafted or corrupted `last_crl_number = 0` is treated identically to "no stored value" (filtered out before the fallback) so defence-in-depth survives a truncated-but-valid-looking file. The `revoke` hot path now regenerates the CRL **before** `persist`, capturing the bumped serial atomically with the new revoked entry; the initial CRL issued in `RevocationStore::new` is followed by an explicit `persist` so a crash between startup and the first revocation cannot re-issue the same `crlNumber`. - **Cap audit-chain rewind budget and enforce minimum archive rotation cadence** — closes both halves of #811. **F-32**: `rustgate_core::audit_chain::read_chain_tip` previously read the entire audit log into memory via `file.read_to_end(&mut bytes)?` at every startup and, on any torn-line recovery, recursed by re-opening and re-reading the whole file from scratch — a hostile or accidentally-enormous log (e.g. 10 GiB of garbage) could stall the tip-recovery phase for minutes and, with each corrupt trailing record, walk the whole file again, compounding the delay into an effective startup DoS. The function is now refactored to seek to `file_len.saturating_sub(REWIND_BUDGET)` (16 MiB) and read only the trailing window, drops any partial leading record that straddles the budget boundary, and walks torn/corrupt trailing records in a bounded iterative loop (not recursive) whose worst-case work is `O(REWIND_BUDGET)` regardless of file size. The container-image attestation is gated behind `continue-on-error: true` on the post-sign best-effort block in `release.yml` so an SBOM generation or attestation hiccup does not un-ship an already-signed image; consumers who require attested SBOMs gate admission on the attestation's presence, not on the release job's exit code. F-78 (Trivy scan gates cosign sign) was already addressed in #777; this PR closes the remaining two sub-items in the same triple. (#778)
- **Reject federation RPC when mTLS client-cert CN is unavailable** — the V2 gRPC `FederationService` previously fell back to the remote IP address when `request.peer_certs()` returned no cert or when `x509_parser` failed to extract a CN, logging only a `warn!` and proceeding. A peer presenting an expired, malformed, or missing cert would then be identified by IP and could silently match an IP-keyed `peer_groups` allow-list entry previously populated by a legitimate peer on the same address — a `send_one_event`, `health_check`, or streaming RPC would be processed under that stolen identity, reaching the authorization and hop-count checks. `peer_id_from_request` now returns `Result<String, Status>`; on any extraction failure it emits the new `audit::federation_peer_rejected(remote_addr, reason)` event and short-circuits every RPC handler (`send_one_event`, `health_check`, `server_event_stream`, `binary_message_stream`, `server_rol_stream`, `client_federate_groups_stream`) with `Status::unauthenticated` before any group or hop-count evaluation runs. The `reason` tag distinguishes `peer_cert_missing` (non-mTLS connection) from `peer_cert_unparseable_or_empty_cn` (cert present but subject CN absent after DER parse and control-char stripping) so operators can triage deployment misconfigurations separately from malformed-cert probes. Non-mTLS testing paths that relied on the previous IP fallback must now supply a real client certificate; the `v2_integration` test harness is migrated to TestCa-backed mTLS to match the production invariant. (#759)
- **Sanitize peer-controlled fields and hash client CNs in structured logs** — the federation gRPC server in `rustgate_federation::v2::server` emits a `warn!` with the offending group name when a peer claims a group it is not authorized for. `group` was logged raw, so a malicious peer could register a group name containing `\r\n[audit] forged=true\r\n` and forge an entire fake audit record in text-mode log output (the JSON layer is not vulnerable, but the default `tracing_subscriber::fmt` text formatter is, and operators often run mixed pipelines). `group` is now routed through `rustgate_core::sanitize::sanitize_for_log` on both call sites — the single-event `validate_event_groups` path and the streaming `send_event_stream` path that logs the full `federate_groups` vector. A regression test attaches a capturing `MakeWriter` to the `rustgate_federation::v2::server` target, pushes an event with an attacker-crafted group name, and asserts no raw `\r\n` survives into the captured bytes and no line in the output begins with the forged marker. Separately, `rustgate_websocket` and `rustgate_mqtt` session handlers replaced 24 raw `cn = %identity.cn` / `cn = %cn` tracing-field emissions (session start/end, CONNECT/DISCONNECT, subscribe/unsubscribe, client-ID collisions, rate-limit drops, replay drops, tenant-quota rejections, keep-alive timeouts) with `cn = %hash_cn(&…)` so production logs carry a 48-bit PII-safe correlation token per MEMORY.md / shared-infrastructure.md convention, matching the existing pattern in `rustgate_transport::router`. Audit events that genuinely need the raw CN for compliance retain it via `rustgate_core::audit::*` functions. (F-153, #802)
- **Fail closed on stale store-forward queue without persistent HMAC key** — `rustgate_transport::ClientQueue::open` (and `open_with_hmac_key(.., None)`) previously generated a fresh random HMAC key on every invocation. When the on-disk queue already contained entries from a previous run, the new key could not verify the old tags, so every stored message was silently discarded on the next drain — a direct violation of the store-forward contract. `ClientQueue::open` now returns a new `StoreForwardError::StaleQueueWithoutKey` error when rebuilt-index depth is non-zero and no persistent key was supplied. The server binary gains two new flags to disambiguate operator intent: `--client-queue-key-file <path>` (env `RUSTGATE_CLIENT_QUEUE_KEY_FILE`) loads a 32-byte hex-encoded HMAC key subject to the same owner + 0600/0400 permission gate as the HTTP-egress secret files; `--client-queue-wipe-on-start` (env `RUSTGATE_CLIENT_QUEUE_WIPE_ON_START`, mutually exclusive with `--client-queue-key-file`) calls the new `ClientQueue::open_with_wipe` which clears the on-disk tables and emits a `store_forward.key_rotated` audit event (with `reason=explicit_wipe_on_start` and the pre-wipe depth) so the deliberate data loss is visible in the compliance audit trail. Operators who restart the server without either flag on a directory that contains stored entries will now see the server refuse to start instead of silently losing queued messages. (#740)
- **Owner check on HTTP egress secret files** — `rustgate_http::auth::read_secret_file` now verifies that the secret file's owning UID matches the running process's effective UID on Unix, in addition to the existing `mode & 0o077 == 0` permission-bit gate. Catches the misconfiguration where a secret is dropped by `root` with correct 0600 permissions but the service runs as a different user — the read would previously succeed silently, leaving operators unaware that the file is outside the service account's lifecycle. (#829)
- **Harden authz obligation actuation** — closes nine gaps surfaced by a post-merge security audit of the obligation data-plane feature (#717): (1) `MaskPoint` bypass via case variation, namespace prefix, or attribute-budget trip — the matcher in `rustgate_cot::mask` now strips optional `ns:` prefixes, does ASCII-case-insensitive comparison, and propagates attribute-budget errors so the caller fails closed instead of leaking coordinates; (2) `apply_mask_point` ignored `strip_coordinates` errors — now splits on payload intent (non-XML passes through with `recovery = "forwarded_unmasked"`, XML-intent parse failure erases the payload with `recovery = "dropped"`) and emits a new `authz.obligation_failed` audit record on every recovery path; (3) `send_to_session` persisted the *post-Receive* form of the payload to the store-forward queue, causing `TagClassified` audit records to fire for messages that never went over the wire and double-actuating Receive-side obligations on drain — now persists the pre-Receive form so `filter_offline_messages` re-evaluates the Receive PEP against the current policy snapshot; (4) unknown `Obligation` variants (the enum is `#[non_exhaustive]`) now emit an `authz.obligation_unknown` audit record so operators running a stale transport against a newer authz engine detect the skew via the audit trail. Both new audit events carry `destination_kind` (direct/group/broadcast/multicast) so SIEM rules can distinguish unicast from fan-out failures. (#734)
- **Advisory scan now gates the build** — removed `continue-on-error: true` from both the `cargo deny check` and `cargo audit` steps in the PR CI workflow. These guards were originally added to tolerate an upstream advisory-DB parse failure (RUSTSEC-2025-0138 malformed TOML), but once the underlying DB was fixed the guards stayed in place and silently masked every subsequent real advisory — a new CVE in a production dependency would have produced a yellow check mark instead of a failing build. The `--ignore` list for individually-reviewed advisories (RUSTSEC-2025-0134 unmaintained-no-replacement, RUSTSEC-2026-0049 mitigated-at-transport-layer) is preserved, each with a dated reviewer note; new suppressions require an explicit ignore entry and a rationale. A prerequisite `rustls-webpki` bump from 0.103.11 → 0.103.12 was required to land this change (fixes RUSTSEC-2026-0098 URI name-constraint bypass and RUSTSEC-2026-0099 wildcard name-constraint bypass). (#777)
- **Release signature gated on Trivy pass** — the `Release Docker Image` workflow previously ran the Trivy container scan *after* `cosign sign` with `continue-on-error: true`, meaning a CRITICAL or HIGH vulnerability in the shipped image did not fail the release: the image was pushed, signed, and announced regardless. Trivy now runs *before* `cosign sign` with `exit-code: '1'` and no `continue-on-error`, so a CRITICAL/HIGH finding short-circuits the job and leaves the image unsigned — consumers who require a cosign signature for admission control will correctly refuse to pull it. The SARIF upload step still runs after sign with `!cancelled()` so findings appear in the GitHub Security tab whether the release succeeded or failed, aiding triage. To ship an image despite a known finding, add a dated entry to `.trivyignore` with reviewer rationale rather than relaxing `exit-code` or re-introducing `continue-on-error`. (#777)

### Fixed

- **Deflake `sign_client_valid_csr` and sibling enrollment integration tests against server-startup race** — `rustgate_enrollment` integration tests spawn `EnrollmentServer::run` in a detached tokio task via `spawn_server_with`, which returns immediately before the server has bound its TCP listener. The `send_request` helper then called `TcpStream::connect(self.addr).await.expect("TCP connect")` with no retry, producing an intermittent `ConnectionRefused` on loaded CI runners — observed in issue-triage trails and reproduced in PR #977's test job. A new `connect_with_retry(addr)` helper at the top of `server_integration.rs` retries `TcpStream::connect` up to ~2 s (100 iterations × 20 ms backoff), panicking with the last error if the server never comes up; all six `send_request` call sites route through it via a single replacement of the raw `TcpStream::connect` call. This is purely a test-infrastructure fix — the enrollment server is unchanged — but the race touches every test in the file, so one fix unblocks the whole suite. Five consecutive local runs of the 10-test integration binary pass; before the fix, the race was visible under CI load. (#982)
- **Align federation JWT clock-skew tolerance with heartbeat timeout to stop `peer_connected` / `token_rejected` flap** — `rustgate_federation::jwt::MAX_CLOCK_SKEW_SECS` is raised from 60 s to 120 s so JWT `iat` validation no longer rejects tokens issued by a peer whose clock drifts inside the window where heartbeats still declare the link alive (`FEDERATION_HEARTBEAT_TIMEOUT = 90 s`). Previously, any NTP drift between 60 s and 90 s produced an observable flap: the liveness check accepted each new mTLS session, the very next token refresh failed `iat > now + 60`, the connector tore the session down with `token_rejected`, reconnected, and re-flapped indefinitely — visible in the audit trail as an unbounded stream of `federation_peer_connected` / `token_rejected` pairs against the same peer CN. A new `const _: () = assert!(MAX_CLOCK_SKEW_SECS >= FEDERATION_HEARTBEAT_TIMEOUT.as_secs(), ...);` compile-time guard pins the invariant so a future tweak to either constant cannot silently reintroduce the flap, and a runtime regression test (`clock_skew_exceeds_heartbeat_timeout`) plus a scenario test (`iat_at_heartbeat_timeout_drift_accepted`) assert that a peer drifting at the full heartbeat-timeout bound still has its tokens accepted. 120 s was chosen over 90 s (exact alignment) so the new tolerance has a 30 s safety margin above the heartbeat timeout — enough to absorb stateless jitter — without materially widening the replay surface compared to the old 60 s window; operators whose environment requires larger drift should also raise heartbeat timeouts, not just this value. (#764)
- **Unblock the docs-site build by dropping an unreachable intra-doc link in `rustgate-server`** — `cargo doc --workspace --no-deps` (the exact invocation in `.github/workflows/docs.yml` with `RUSTDOCFLAGS=-D warnings`) has been failing on every push to `main` since `rustgate-mqtt` was made an optional dependency of `rustgate-server`. The `MqttWildcardPolicy` doc comment in `crates/rustgate-server/src/cli.rs` included `[` `rustgate_mqtt::WildcardPolicy` `]` as an intra-doc link, but that crate is only in scope when the `mqtt` cargo feature is enabled — and the docs workflow builds with default features only, so rustdoc emits `unresolved link to rustgate_mqtt::WildcardPolicy` as a hard error under `-D warnings`. The link is demoted to a plain code span (`` `rustgate_mqtt::WildcardPolicy` ``) with a one-sentence expansion of the doc comment explaining why the cross-crate link cannot be used here. No behaviour change; restores green docs CI on `main`.
- **HTTP admission-queue drops no longer bypass the dead-letter queue** — `rustgate_http::HttpPublisher::publish` previously silently dropped messages when the bounded dispatch channel was full or closed; only circuit-open drops reached the DLQ. This left operators with no forensic trail for messages shed during load spikes or shutdown. The admission-full and admission-closed paths now persist the message to the DLQ under the synthetic target name `admission` (when the DLQ is configured) and increment the new `rustgate_http_dropped_total{reason}` counter. `TlsConfig::pin_sha256` docs are also expanded to explicitly state that pins hash the **entire leaf certificate DER** (not SPKI, so not RFC 7469); rotating a certificate always breaks the pin, which was previously under-documented. New pinning regression test `pin_is_full_leaf_der_not_spki_or_subject` codifies the semantic so a future migration to SPKI pinning cannot silently break deployed pins. (#813)
- **O(1) JWT revocation-cache eviction** — `rustgate_federation::jwt::JwtAuthority::revoke` replaced its `HashMap<String, u64>` + `min_by_key` full-scan eviction with an `lru::LruCache<String, u64>`, turning the `O(n)` per-call eviction into `O(1)` and eliminating the `O(n²)` worst case that made the cache a DoS amplifier on large revocation bursts at capacity. The old code also drained the oldest-expiring entry on every capacity hit — now LRU ordering naturally evicts the oldest-inserted token, which matches the original "min_by_key exp" semantic closely since tokens issued together share similar expirations. Expired entries are purged via an amortized sweep every 128 `revoke` calls (bounded O(n/128) cost), so stale `exp`s still leave the cache without per-call scan overhead. `validate()` uses the non-promoting `LruCache::peek` so a flood of valid validations against a revoked `jti` doesn't keep it at the front forever, preserving the eviction policy under read load. `with_revocation_capacity(0)` is coerced to `NonZeroUsize::MIN` at the type boundary (was previously `max(1, n)`). (#761)
- **Disable Nagle on every TCP socket to remove ~40 ms tactical-message latency** — rustgate's traffic pattern is small interactive messages (tactical CoT position updates are 200–800 bytes, federation control RPCs, WebSocket frames, MQTT CONNECT/SUBSCRIBE exchanges, enrollment request/response pairs). With Nagle's algorithm on and the peer's delayed-ACK timer at its Linux default (`TCP_DELACK_MIN = 40 ms`), a single small write followed by `poll_flush` routinely stalled a full RTT per message because the kernel held the outbound segment waiting for more data. A workspace-wide audit confirmed that `set_nodelay` was called **nowhere** — neither on listener-accepted sockets nor on client dial sockets — so every protocol adapter paid the penalty: TAK TLS and plaintext listeners, WebSocket and MQTT handshakes, federation gRPC dials, HTTP metrics scrapes, enrollment endpoints, and the `rustgate-client` library. `rustgate_core::net` gains `configure_tcp_nodelay(&stream)` and `configure_tactical_socket(&stream)` (the combined keepalive + `TCP_NODELAY` helper). Every call site that previously invoked `configure_tcp_keepalive` now calls `configure_tactical_socket` instead, so a future transport cannot add keepalive and silently forget Nagle-disable. The `rustgate-client` dial path — which had neither keepalive nor `TCP_NODELAY` before — gains both. A new integration test in `rustgate-transport::plaintext::tests` asserts `TCP_NODELAY = 1` end-to-end on an accepted socket so a regression fails CI instead of re-introducing the latency penalty. (#745)
- **Legitimate equatorial position reports no longer dropped by NATS publisher** — the "is this position unknown" filter in `rustgate_nats::publisher` previously matched `lat == 0.0 && lon == 0.0`, silently dropping every valid fix from the Gulf of Guinea and adjacent equatorial waters. The filter now keys on the `ce`/`le` (circular/linear 1-sigma error) fields instead, with a 1,000 km threshold that catches both the common TAK sentinel (`9999999`) and the MITRE reference-GUI sentinel (`999999999`) without a false positive on any realistic GPS/INS error. Earth's equatorial radius is ~6,371 km, so 1,000 km is both well above any legitimate error and below every observed sentinel. See the MITRE CoT Message Router User's Guide (MP090284) Table 2-1 and Figure 6-5 for the underlying spec. (#829)

### Changed

- **Reject out-of-range lat/lon per WGS-84 spec** — the CoT parsers in `rustgate-cot` and `rustgate-proto` now reject `<point>` elements whose `lat` is outside `[-90.0, 90.0]` or `lon` is outside `[-180.0, 180.0]`, matching the WGS-84 decimal-degree ranges defined in MITRE CoT Message Router User's Guide (MP090284) Table 2-1. Non-finite values (NaN, ±∞) are also rejected. `rustgate_cot::ParseError` gains an `OutOfRange { field, value }` variant and `rustgate_proto::ProtoError` gains a matching `OutOfRange { field, value }` variant. Previously these malformed coordinates parsed successfully and propagated through the router, allowing spoofed or corrupt tracks outside the Earth surface to reach downstream consumers. (#933)
- **Preserve CoT `<event version>` through the XML→JSON wire path** — `rustgate_proto::xml_full::FullCotEvent` now captures the `version` attribute on `<event>` (previously silently discarded), and `WireEvent::from_full_cot` in `rustgate-nats` emits that captured value on the JSON wire instead of hardcoding `"2.0"`. Required by MITRE CoT Message Router User's Guide (MP090284) Table 2-1, which lists `version` as a mandatory attribute. When the source XML omits the attribute, the JSON wire falls back to `"2.0"` so downstream consumers always see a conforming schema token. (#931)
- **Reject malformed CoT timestamps at XML parse time** — `rustgate_proto::xml_full::parse_full` now validates `<event>` `time`, `start`, and `stale` attributes as ISO 8601 / RFC 3339 UTC timestamps (`YYYY-MM-DDThh:mm:ss[.SSS]Z`) at parse time, using the same `iso8601_to_millis` validator the protobuf conversion path already relies on. Previously these attributes were forwarded as opaque strings through the XML→JSON NATS wire and the XML→protobuf conversion re-validated downstream, so a malformed timestamp could propagate into the routing layer before being rejected. Required by MITRE CoT Message Router User's Guide (MP090284) Table 2-1. Empty / omitted attributes are still accepted (the "attribute present" check remains orthogonal); only non-empty strings that fail to parse are rejected with `ProtoError::InvalidTimestamp("<field>: <reason>")`. The minimal `rustgate_cot::parse` (routing-focused, TTL-only use of timestamps) keeps its existing silent-fallback behavior — strict enforcement lives in the full-detail parser where downstream consumers actually care about timestamp validity. (#937)
- **Descriptive error and expanded docstring for ACL group-id validation** — `rustgate_server::acl_api::valid_group_id` now returns the human-readable rule (`"group id must be 1–128 bytes and contain only ASCII alphanumeric or `_`, `.`, `:`, `-`"`) to clients that submit a malformed group name, instead of the previous opaque `"invalid group id"`. The function's docstring is expanded to explain why the allow list is ASCII-only (downstream NATS subject tokenisation, case-insensitive router lookup, X.509 OU extraction, and structured-logging compatibility) and why the 128-byte cap aligns with `MAX_CN_LENGTH`. (#829)

The new `#[cfg(test)] mod tests` in `packet.rs` adds 16 unit tests pinning: (a) the 10-byte incremental-read threshold and the level-offset-beyond-buffer case both return `Ok(None)` without committing to a protocol level, (b) a non-CONNECT first packet (`\x30…` PUBLISH) is rejected with `MqttError::ConnectExpected` and leaves `protocol` unset, (c) legacy protocol level 3 (MQTT 3.1 / MQIsdp) is rejected with `UnsupportedProtocol(3)` so operators can triage via the raw error, (d) valid level-4 and level-5 CONNECTs negotiate `ProtocolLevel::V311` / `ProtocolLevel::V50` and fully consume the buffer, (e) post-handshake `try_parse` with a pinned protocol decodes PUBACKs via the correct version codec without re-entering the negotiator (a regression here would route every non-CONNECT v5 packet through the v4 parser), (f) insufficient bytes return `Ok(None)` and malformed frames return `MqttError::Malformed(_)` so the outer I/O loop has a clear "read more" vs. "abort session" dispatch, (g) `try_parse` with `protocol: None` delegates to the CONNECT negotiator even for non-CONNECT input so the first-packet-must-be-CONNECT invariant can never be bypassed by re-framing, (h) v4 CONNACK and PUBLISH round-trip cleanly through `mqttbytes::v4::read`, (i) the v4 server-only-silent-noop arm produces zero bytes for Connect / Subscribe / PingReq (pinning the contract so flipping to panic-on-unknown would fail CI), (j) v5 CONNACK round-trips with the `ConnAckProperties::new()` workaround for the mqttbytes 0.6 `None`-properties serialization bug, and (k) v5 Disconnect produces non-empty output with the correct fixed-header type (server-initiated disconnects would otherwise be indistinguishable from "client reset TCP" on the wire). When enabled with `--ocsp-stapling` (env `RUSTGATE_OCSP_STAPLING`), the server's certificate resolver is wrapped with `ocsp_stapler::Stapler`, which fetches OCSP responses for the active certificate in a background tokio task and attaches them to the handshake so clients can verify revocation status without contacting the issuing CA. Coexists with the existing CRL-based client certificate verification (the two operate on opposite sides of the handshake). Most useful with enterprise/private CAs that operate their own OCSP responder; Let's Encrypt dropped OCSP support in 2025. The first handshakes after startup may be served without a stapled response until the background fetcher completes its initial cycle. The stapler is gracefully stopped during shutdown. (#524)
- **Per-identity Prometheus metrics with bounded cardinality** — `rustgate_messages_routed_total` and `rustgate_messages_dropped_total` now carry an `identity_cn` label so operators can attribute routing volume and rate-limit drops to individual clients. Cardinality is bounded by an optional CN allowlist loaded from `--metrics-identity-allowlist` (env `RUSTGATE_METRICS_IDENTITY_ALLOWLIST`, one CN per line, `#` comments allowed); CNs not in the allowlist — and **all** CNs when the allowlist is unset — collapse into the literal `"other"` bucket, capping per-identity cardinality at 1 by default. New `--metrics-per-identity` flag (env `RUSTGATE_METRICS_PER_IDENTITY`, default false) opt-in registers Tier 2 per-identity metrics: `rustgate_per_identity_handshake_failures_total`, `rustgate_per_identity_session_duration_seconds`, `rustgate_per_identity_bytes_sent_total`, and `rustgate_per_identity_bytes_received_total`. Tier 2 metrics are not registered when the flag is disabled, imposing zero overhead. (#526)
- **SIGHUP config reload** — on Unix, sending `SIGHUP` to the running server now reloads the server certificate (via the existing `CertReloader`), the group ACL policy (via the existing `AclReloader`), and re-validates the configured CRL file from disk. Each component is reloaded independently — failures in one do not abort the others — and structured `target="audit", event_type="config.reload"` events are emitted per component with `result=success|failure`. SIGHUP reload is Unix-only; on other platforms the handler is not installed. CRL reload re-parses and freshness-checks the file but does not yet swap CRLs into the live TLS listener; applying CRL changes to in-flight handshakes still requires a server restart. (#528)
- **ACL REST API authentication** — new `--acl-api-token-file` CLI flag (env `RUSTGATE_ACL_API_TOKEN_FILE`) guards the `/api/acl/` endpoints with a bearer token. When unset, the ACL API is not registered at all and `/api/acl/` requests fall through to 404. When set, every request must present `Authorization: Bearer <token>` and the token is compared in constant time. Mutations (`PUT`/`DELETE`) are now persisted atomically to the configured `--group-acl-file` (write-to-tmp + fsync + rename) and the hot reloader's cached hash is updated so the next poll does not re-detect the change. Group identifiers are validated against a strict `[A-Za-z0-9_.:-]{1,128}` allow list. (#538)
- **JSON audit log sink** — new `--audit-log` CLI flag (env `RUSTGATE_AUDIT_LOG`) writes audit events as JSON lines to a dedicated file, separate from the main log stream. Filters only `target="audit"` events using a per-layer `Targets` filter. Use `"-"` for stdout. Audit events now include `session_id` on connect/disconnect for correlation. (#525)
- **ACL deny rules** — `GroupAcl` now supports optional `deny_send` and `deny_receive` lists alongside the existing allow lists. Deny is evaluated first and overrides allow, enabling fine-grained block-list semantics: a CN appearing in a deny list cannot send/receive even when also in the allow list. With an empty allow list, the deny list acts as a pure block list (the group is open except for denied CNs). Legacy ACL JSON files without `deny_send`/`deny_receive` continue to parse unchanged. (#523)
- **ACL management REST API** — new `/api/acl/` endpoints exposed on the metrics HTTP server (mirrors the `/api/federation/` pattern). Supports `GET /api/acl/groups` to list current rules, `PUT /api/acl/groups/{group}` to upsert an entry, `DELETE /api/acl/groups/{group}` to remove one, and `POST /api/acl/reload` to re-read the on-disk ACL file. Mutations rebuild the full policy and atomically swap it on the router via `ArcSwap`. (#522)
- **Hot-reloadable ACL** — the group access control policy can now be updated at runtime without restarting the server. The router's ACL is stored in an `ArcSwap` for lock-free reads, and a new `--acl-reload-interval` CLI flag (env `RUSTGATE_ACL_RELOAD_INTERVAL`, default 0 = disabled) enables periodic polling of the `--group-acl-file` for changes. File changes are detected via SHA-256 hash comparison; only modified files trigger a policy swap. Audit events are emitted on reload success and failure. (#521)
- **Message priority channels** — replaced the single per-session mpsc channel with a dual-channel approach: a high-priority channel (capacity 16) for Position and Alert messages, and a normal-priority channel (capacity 64) for all other message types. Write loops use biased `tokio::select!` to always drain priority messages first, ensuring time-sensitive situational awareness data is delivered ahead of bulk traffic. The circuit breaker applies across both channels. (#519)
